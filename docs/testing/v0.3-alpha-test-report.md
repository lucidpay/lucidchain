Tested commit `385ac45` (v0.3-Alpha plus the attestation and dispute commits) on a single-validator local testnet, `my-testnet-1`, on 9 October 2026.

## How we tested

- **Test genesis:** secp256k1 allowed for sidechains and attestors, `auto_activate` true, exit cooldowns 120 s, missed-checkpoint grace 60 s, gov voting period 40 s. Everything else default.
- **Signing:** throwaway secp256k1 and ML-DSA-65 keys generated in memory, signing with the repo's own `CheckpointSignBytes` and `tx attestor sign-bytes`. Real gnark Groth16 and PLONK proofs were bound to on-chain checkpoints with `ComputeBinding`.
- **Transactions:** every check went through `lucidchaind tx` against the live node. A check passed only if the outcome (accepted or rejected) and the rejection reason matched the expected ones.

## C1 · Proofs module not wired into the app

### Summary
On a running node, `MsgRegisterVerifier` fails for every proof system with `no verifier implementation compiled into this binary`, including `groth16-bn254`. No verifier can be registered, so no proof can be submitted. The proofs module doesn't work end to end.

### Cause
In `x/proofs/module/depinject.go`, two `ModuleInputs` fields are unexported:

```go
checkpointKeeper types.CheckpointKeeper
impls            map[string]types.ProofVerifier
```

depinject only fills exported fields, so the keeper is built with a nil checkpoint keeper and an empty verifier map. Nothing supplies `verifiers.Default()` to the container either. The keeper unit tests construct the keeper directly, so they don't catch this.

### Steps to reproduce
1. Build `main` (385ac45) and start a local testnet.
2. Submit a gov proposal with `/lucidchain.proofs.v1.MsgRegisterVerifier`, `proof_system_id: groth16-bn254` and a valid gnark verifying key.
3. Vote yes. The proposal ends `PROPOSAL_STATUS_FAILED` with `"groth16-bn254": no verifier implementation compiled into this binary`.

### Fix (tested)
```diff
--- a/x/proofs/module/depinject.go
-	checkpointKeeper types.CheckpointKeeper
+	CheckpointKeeper types.CheckpointKeeper
 	BankKeeper       types.BankKeeper
-	impls            map[string]types.ProofVerifier
+	Impls            map[string]types.ProofVerifier
...
-		in.checkpointKeeper,
+		in.CheckpointKeeper,
 		in.BankKeeper,
-		in.impls,
+		in.Impls,
--- a/app/app.go
+	proofsverifiers "github.com/lucidpay/lucidchain/x/proofs/verifiers"
...
 			map[string]module.AppModuleBasic{ ... },
+			// proof verifier implementations compiled into the binary
+			proofsverifiers.Default(),
```

With this patch, on the same chain:
- `groth16-bn254`, `groth16-bls12-381` and `plonk-bn254` registered.
- A garbage verifying key and an unknown system id were refused.
- Real gnark Groth16 and PLONK proofs bound to on-chain checkpoints verified.
- Correctly rejected: duplicates, proofs bound to another checkpoint or claim, a valid proof with another claim's public inputs (`pairing doesn't match`), a corrupted proof, the wrong curve, an unknown checkpoint, oversize proofs, and a deprecated verifier.

An app-level test that builds the real app and registers a verifier would prevent this kind of wiring regression.

## C2 · Exit bonds are never returned

### Summary
After `exit` (sidechain) or `initiate-attestor-exit` (attestor), the bond is never returned. Both modules have a `ProcessExits` keeper function that releases bonds once the cooldown passes, but nothing calls it. Every module's `EndBlock` returns `nil`.

`x/sidechain/keeper/abci.go` itself says: *"Wire it into the module's EndBlock."*

### Steps to reproduce (sidechain)
1. Set `app_state.sidechain.params.exit_cooldown_seconds` to `"120"` in genesis and start the chain.
2. Register a sidechain with a 10,000,000stake bond, then run `lucidchaind tx sidechain exit <id>`.
3. After `bond_return_at` passes, `q sidechain sidechain <id>` still shows `bond: 10000000`, the module account still holds it, and the operator's balance is unchanged.

Observed:
- Sidechain `sc-prov`: `bond_return_at` 19:10:59 UTC; at 19:11:36 the 10,000,000stake bond was still held.
- Attestors `acme` and `beta` (after `initiate-attestor-exit`): `bond_return_at` 20:15:26 and 20:15:31; at 20:16:34 their 1,800,000 and 1,000,000stake bonds were still in the attestor module account.

### Impact
Every bond posted by an exiting sidechain or attestor stays locked in the module account forever.

### Fix (tested)
Call the existing functions from `EndBlock` in both modules:

```go
// x/sidechain/module/module.go and x/attestor/module/module.go
func (am AppModule) EndBlock(ctx context.Context) error {
	return am.keeper.ProcessExits(ctx)
}
```

Restarting the same chain with this change, the first block released every overdue bond exactly: the operators got back 10,000,000 (`sc-prov`), 1,800,000 (`acme`) and 1,000,000 (`beta`). The attestor module account was left empty, and the sidechain module kept exactly the 8,000,000 bonded by the 4 sidechains that are still active.

## H1 · Missed checkpoints never suspend a sidechain

### Summary
Spec §2.6 says the sidechain `EndBlocker` moves an `ACTIVE` sidechain to `SUSPENDED` once `checkpoint_interval_seconds` + `missed_checkpoint_grace_seconds` pass without a checkpoint, and emits an event. Nothing in the code does this. The param is only stored.

### Steps to reproduce
1. Set `missed_checkpoint_grace_seconds` to `"60"` in genesis.
2. Register a sidechain with `--checkpoint-interval-seconds 10` and submit checkpoint 1.
3. Wait. More than 10 minutes later, `q sidechain sidechain <id>` still shows `SIDECHAIN_STATUS_ACTIVE`.

### Expected
`SIDECHAIN_STATUS_SUSPENDED` (and an event) after about 70 s.

## H2 · Sidechain bonds can never be slashed

### Summary
The spec's `SlashBond(ctx, id, reason, amount)` keeper method (§2.4) doesn't exist, and no code path sets `SIDECHAIN_STATUS_SLASHED`. A sidechain's bond can never be lost, so today it gives no economic security.

A related point: `InitiateSidechainExit` accepts sidechains in `SUSPENDED` and `SLASHED` status. Once exit bonds are released (see C2), an operator suspended for a fault could exit and recover the full bond.

### Suggested
Implement `SlashBond` per the spec, and decide whether a suspended or slashed sidechain may exit, or whether its bond is frozen until governance decides.

## H3 · CLI rejects ML-DSA-65 signer keys

### Summary
`allowed_pubkey_type_urls` defaults to `/cosmos.crypto.mldsa65.PubKey` only, for both sidechains and attestors. But the CLI can't parse that type:

```
invalid argument "{\"@type\":\"/cosmos.crypto.mldsa65.PubKey\",\"key\":\"...\"}" for "--signer-keys" flag:
proto: (line 1:10): unable to resolve "/cosmos.crypto.mldsa65.PubKey": "not found"
```

This affects `register-sidechain`, `update-signers`, `register-attestor` and `update-attestor-signers`. With default params, no sidechain or attestor can be registered from the CLI.

### The chain itself is fine
Building the tx with `--generate-only`, swapping the ML-DSA-65 keys into `signer_keys` with `jq`, then `tx sign` + `tx broadcast`, registered a sidechain with three ML-DSA-65 keys (`ACTIVE`). Checkpoints signed by those keys were accepted: 2-of-3 for about 434k gas, 3-of-3 for about 520k gas. A secp256k1 signature in an ML-DSA slot was rejected.

### Likely fix
autocli resolves `Any` types through the global protobuf registry, which apparently doesn't have the mldsa65 key's descriptor. Register it there, or give these commands a custom flag that takes raw key bytes and a type.

## H5 · Attestor conflict-of-interest check is not implemented

### Summary
`readme.md` §4.6 says: *"Conflict-of-interest enforcement (an attestor may not be the sidechain's own operator) is checked at `MsgRegisterAttestor` time by comparing `operator` addresses, and re-checked at `MsgSubmitAttestation` time against the target sidechain's registered `operator`."*

Neither check exists:
- `SubmitAttestation` (`x/attestor/keeper/msg_server_attestation.go`) checks that the schema is active, that the submitter is the attestor's own operator, the attestor's status and schema authorisation, the signer-set version, the payload, that the checkpoint exists, duplicates, and the signatures. It never loads the target sidechain or compares the attestor's operator with the sidechain's.
- `x/attestor` has no sidechain keeper dependency (`x/attestor/types/expected_keepers.go` defines auth, bank and checkpoint keepers only), so it can't look up a sidechain's operator.
- `MsgRegisterAttestor` has no sidechain field, so a registration-time check would need to compare against every registered sidechain; the spec doesn't say how.

### Observed on the test chain
Attestor `beta` and sidechain `sc-a` have the same operator, `cosmos18353j95lc0d7pmaj7kfrjacwhf80f75p99n9dr` (the `validator` key). `beta` submitted an attestation (`kyc-v1`) on `sc-a` checkpoint 1 at height 78 and it was accepted. That attestation is `ATTESTATION_STATUS_UPHELD` after the dispute test.

### Suggested
Give `x/attestor` a sidechain lookup and reject `MsgSubmitAttestation` when the attestor's operator equals the sidechain's operator. Add a test for the same-operator rejection and for an independent attestor.

## H6 · Verifier infrastructure faults are recorded as invalid proofs

### Summary
`x/proofs/types/verifier_fault.go` sets a consensus rule: a `Verify` error that satisfies `errors.Is(err, ErrVerifierFault)` (verifier crashed, timed out, was unreachable, or reported the wrong image hash) *"must NEVER be recorded as 'proof invalid'"*; the node must halt and retry instead.

`SubmitProof` doesn't follow it. `x/proofs/keeper/keeper.go:316-319` turns every `Verify` error into `errorsmod.Wrap(types.ErrInvalidProof, err.Error())`. Because only the error text is kept, the `ErrVerifierFault` identity is lost, and nothing in `x/proofs/keeper` checks for `ErrVerifierFault`. The `safely` helper (`keeper.go:223`) likewise turns a panic into a plain `fmt.Errorf` error.

### When it matters
The only verifier that returns `ErrVerifierFault` is the external PQ verifier adapter (`x/proofs/verifiers/qp.go`). `verifiers.Default()` contains only the four gnark verifiers, so with the default build no verifier returns this error today. Once the PQ verifier is enabled, a local fault on one validator would make that validator reject a proof that validators without the fault accept.

### Suggested
Check `errors.Is(err, types.ErrVerifierFault)` before wrapping, and decide how a fault stops block execution. A panic inside a message handler doesn't do it: `runTx` recovers panics and returns them as a tx error (`baseapp/baseapp.go:807-811` in Cosmos SDK v0.55.0). Test it by injecting a transport failure.

### What was run

- **Symbol level** (the default, which checks whether vulnerable functions are actually called): not completed. It was killed for running out of memory on our 3.8 GB test server, so we can't say which of the findings below are reachable from LucidChain's code.

## Medium
- **`auto_activate` defaults to `false`.** A fresh `lucidchaind init` writes `auto_activate: false`, so a newly registered sidechain stays `PENDING` and every checkpoint is rejected. The readme's expected output shows `ACTIVE`, but only the "initialised with old code" block sets `true`. This PR adds the step to the readme; changing the default would remove the need for it.
- **Readme attestation steps fail on a fresh chain.** Attestor `allowed_pubkey_type_urls` allows only ML-DSA-65, but `tools/signbytes/submit-attestation.sh` signs with the validator's secp256k1 key. The readme also skipped the steps it depends on: create schema `kyc-v1` (gov), `register-attestor acme`, activate it (gov). This PR adds them; they were verified on a fresh chain up to `ATTESTOR_STATUS_ACTIVE`.
- **One cheap dispute freezes a whole attestor.** A dispute with the 100,000stake minimum sets the attestor to `SUSPENDED` (all schemas, all new attestations) until governance resolves it. Consider a higher `min_dispute_bond`, or suspending only the disputed attestation.
- **Dispute resolution takes 48 h with default gov params.** The readme's "vote, then check" step won't work for 2 days. Mention it, or use an expedited proposal / shorter `voting_period` for testnets.
- **No tier upgrade.** The spec's `MsgRequestTierUpgrade` isn't in `tx.proto`.

## Low
- **Expired attestations still read `ACTIVE`.** Nothing sets an expired status after `expires_at`. Clients must compare times themselves.
- **Errors include absolute build paths**, e.g. `[/root/lucidchain/x/checkpoint/keeper/keeper.go:184]`. Build with `-trimpath`.
- **All four module accounts have `Minter`, `Burner` and `Staking`** (`app/app_config.go`). None of them mint; drop unneeded permissions.
- **signcheckpoint instructions.** The readme says to put the binary in `~/tools/signcheckpoint/`, then uses `go run ./tools/signcheckpoint`, which only works inside the repo. The `submit-checkpoint` template has a trailing space after `\` on the sidechain-id line, which breaks the line continuation.
- **`exit` skips the pending-exit state.** It moves straight to `EXITED`; the spec describes a pending-exit state during the cooldown.

## Design questions
1. `x/attestor` doesn't check the sidechain's status: attestations on checkpoints of an `EXITED` sidechain are accepted. Intended?
2. A `SLASHED` attestor can `initiate-attestor-exit` and recover the rest of its bond. Intended?
3. The attestor exit cooldown is the longest `dispute_window_seconds` among its schemas (1 h for `kyc-v1`), not `exit_cooldown_seconds`. Worth documenting.
4. Resolved disputes don't store the slashed amount or the challenger reward (events only).
